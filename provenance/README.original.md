# Colorful N14 24 — экспериментальный профиль nbfc-linux

**Статус: офлайн-проверка кода; на ноутбуке не испытан. Не готовый исправляющий прошивку продукт.**

Для COLORFUL N14 24, BIOS 2.07, заявленной пользователем EC 2.0, i7-13620H / RTX 4060. Использует ACPI-интерфейс, восстановленный по модулю N14 из iGameCenter и сопоставленный с DSDT этого ноутбука. Не предназначен для других Colorful, других BIOS или оригинального NBFC для Windows.

## Зачем не обычные EC-регистры

Найденный интерфейс использует WMI/ACPI и пакеты доступа к индексным портам либо отображённой памяти. Их адреса нельзя переносить в стандартную область ACPI EC.

[Транспорт](src/transport.lua:1) обращается только к подтверждённому методу с 24-байтовыми пакетами, выбирая ветку по идентификатору контроллера. Нет прямого доступа через стандартный EC, физическую память или произвольные порты из пользовательского кода.

Это не делает вызовы безрисковыми: ACPI-метод сам обращается к I/O/памяти. Диагностическое чтение индексного порта включает запись индекса, но не настройку скорости. Прошивка не сериализует этот метод; параллельные обращения других утилит могут конфликтовать.

## Кривые

Значения ниже — шкала целевой скорости SDK, **не измеренный PWM**. 100% означает запрос 7000 об/мин, как в максимальном режиме исследованного приложения; реальный максимум ещё не измерен. Номинальные 40% означают запрос около 2800 об/мин и не гарантируют такую фактическую скорость.

| Температура CPU при нагреве | Цель CPU |
|---|---:|
| Ниже 45 °C | 40% |
| 45–59 °C | 50% |
| 60–69 °C | 65% |
| 70–79 °C | 80% |
| От 80 °C | 100% |

| Температура GPU при нагреве | Цель GPU |
|---|---:|
| Ниже 45 °C | 40% |
| 45–54 °C | 50% |
| 55–64 °C | 65% |
| 65–71 °C | 80% |
| От 72 °C | 100% |

При охлаждении действуют отдельные пониженные пороги гистерезиса. CPU использует максимум источников CPU; GPU — максимум источников GPU. Правильное определение RTX 4060 проверяется по журналу службы; скрытого перехода на CPU в профиле нет.

Дополнительные критические пороги: CPU 90 °C, GPU 80 °C. Они не заменяют аппаратную защиту и не означают, что эти температуры нужно достигать при испытании. В исследованном NBFC есть **температурный фильтр на 6000 мс**, поэтому реакция не мгновенная. Интервал опроса профиля — 1000 мс.

Остановка вентиляторов запрещена: обработчик ограничивает даже ручной запрос 0% минимумом 40%. При таком ручном запросе интерфейс NBFC может показывать запрошенный процент, отличный от реально ограниченной команды.

## Защитные ограничения и существенные риски

1. Проверяются DMI производителя и модели, BIOS и точный SHA-256 DSDT:
   **4aab3c89fdaac8ab9e20d31cff3fe0a18b83877442520eb294429ff9237bef06**.
2. Подготовительный скрипт создаёт временное root-разрешение только после проверки. Lua повторно проверяет DMI и идентификатор контроллера. Разрешение исчезает после перезагрузки; не предназначено для ручного редактирования. Это защита от случайного запуска, а не от администратора, намеренно изменяющего файлы.
3. Версия EC аппаратно не считывается. Для управления требуется вручную подтвердить EC 2.0. Совпадение DSDT не гарантирует совпадение прошивки EC.
4. Режим чтения не разрешает запись настроек вентилятора даже при случайном запуске службы без флага чтения.
5. При первом управлении запрашивается максимальная скорость обоих вентиляторов, затем применяются кривые. Не реализована задержка стартового разгона; надёжность запуска при минимуме ещё нужно проверить.
6. Телеметрия не подделывается: нулевые/скачущие значения не заменяются заданной скоростью. Показание выше номинальных 7000 об/мин приводит к ошибке, а не обрезается молча. Реальный диапазон нужно проверить.
7. **При штатном завершении после управляющих записей запрашивается максимум ОБОИХ вентиляторов. Возврат в Normal намеренно не выполняется, поскольку пользователь сообщил о неисправности этого режима.** Не ждать тишины после остановки службы.
8. При ошибке записи выполняется попытка запросить максимум; при устойчивых ошибках службы её обычное завершение также вызывает обработчик максимума. Это best effort, не аппаратная гарантия. Сбой ACPI, зависание, принудительное убийство процесса, выключение питания или авария ядра могут оставить последнее состояние.
9. NBFC не проверяет физический обдув. Даже успешный ответ прошивки не доказывает вращение. Программный обход не ремонтирует тахометр, разъём или двигатель.
10. **Сон, гибернация, пробуждение и автономный автозапуск не проверены. На первом этапе не использовать.** Штатное завершение не является универсальным откатом; в конце теста при необходимости полностью выключить ноутбук и вернуться к уже известному работающему способу охлаждения.

## Подготовка CachyOS

Нужны Python 3, Bash, подходящий nbfc-linux и модуль acpi_call именно для работающего ядра. Пакет заголовков должен соответствовать фактическому ядру CachyOS. Нельзя гарантировать совместимость произвольного готового пакета или модуля по одному названию дистрибутива.

Установку NBFC выполнять по официальной инструкции. Не включать службу автоматически. Если менеджер пакетов сам запустил её, остановить её до наших проверок. Закрыть другие программы управления вентиляторами и низкоуровневого опроса EC/WMI/ACPI. Для Secure Boot использовать корректно подписанный модуль; отключать защиту наугад не требуется.

Вся папка проекта должна находиться на Linux, предпочтительно на обычной Linux-файловой системе. Не копировать только JSON без подготовительных файлов.

### Этап A — проверка без ACPI-вызовов

Открыть терминал в папке проекта и выполнить [sudo python3 prepare.py check](prepare.py:1).

Скрипт не загружает модуль, не устанавливает пакеты и не стартует службу. Если DSDT или модель не совпали — остановиться; не убирать защиту ради запуска. При обновлённом BIOS потребуется повторный анализ.

### Этап B — только диагностическое чтение

Выполнить [sudo bash run-read-only.sh --acknowledge-risk](run-read-only.sh:1).

Это уже **реальные диагностические обращения к контроллеру**. На холодном ноутбуке без нагрузки скрипт:

1. Проверит отсутствие запущенной службы NBFC.
2. Прочитает идентификатор EC и текущие обороты.
3. Создаст разрешение только на чтение.
4. Запустит NBFC в терминале, в режиме чтения.

Сохранить выведенный идентификатор EC в виде двух шестнадцатеричных байтов HH:LL. Не подставлять заранее 20:10: марка ещё не определена.

В журнале должны быть реальные источники CPU и NVIDIA GPU, а не только CPU или ошибочный датчик. Сравнить GPU-температуру с мониторингом NVIDIA. Для дополнительного просмотра NBFC поддерживает [команды sensors list и status](https://github.com/nbfc-linux/nbfc-linux/blob/59b4b4ffacf125cc79c8c7740ff2f2f8ff1343f7/README.md). Наличие датчика в NVIDIA само по себе не доказывает, что он доступен установленной сборке NBFC.

Если NVIDIA GPU спит, источник может отсутствовать. Не подменять его нулевой температурой или CPU. Если GPU-источник недоступен/неверен, к управлению не переходить. На этом этапе исправность вентиляторов не предполагается: не давать нагрузку и не оставлять ноутбук с неподвижным вентилятором нагреваться.

Завершить диагностику сочетанием Ctrl+C. При чтении команды скорости и команды сброса не выполняются.

### Этап C — ограниченный тест управления

Только после проверки обоих источников и идентификатора EC выполнить [sudo bash run-control.sh --acknowledge-risk --sensors-verified --expected-ec-id HH:LL --ec-version 2.0](run-control.sh:1), **заменив HH:LL фактическим результатом этапа B**. Это шаблон команды, не готовый идентификатор.

Эта команда реально меняет управление вентиляторами. Флаги — подтверждение выполненных проверок, а не способ обойти ошибки. Сначала тест без нагрузки. Проверить физический обдув обоих вентиляторов, реальные температуры и отсутствие ошибок. Не считать прыгающие GPU-проценты надёжным подтверждением работы. Не выполнять стресс-тест, не закрывать крышку и не оставлять ноутбук без наблюдения.

Если нет обдува, температура ненормально растёт, RPM недостоверны или появляются ошибки — прекратить нагрузку, завершить тест; если охлаждение не восстановилось, выключить ноутбук. Штатный выход из режима управления запрашивает обеим крыльчаткам максимум. Возврат в Normal не предусмотрен как безопасный откат.

**Не использовать постоянный запуск, пока не проверены:** повторный старт, независимые каналы, минимальная устойчивая скорость, датчики NVIDIA, корректная остановка службы и поведение после сна. Автозапуска в этом пакете нет.

## Особенности NBFC, которые важно знать

- В подготовленной служебной конфигурации выбран [dummy-backend](prepare.py:139). Это отключает стандартный доступ к EC, **но не ACPI-вызовы Lua**. Это не режим симуляции всего профиля.
- Для обоих вентиляторов принудительно выбираются программные кривые вместо ранее сохранённых ручных значений. NBFC может обновить свой глобальный файл состояния. Если NBFC использовался раньше, сохранить его конфигурацию/состояние до теста.
- Из-за нестабильной GPU-телеметрии NBFC может часто считать повторную инициализацию необходимой. В профиле нет записей инициализации, переключающих Normal/Custom. Управляющий обработчик повторяет только один и тот же ручной режим перед записью скорости.
- Автоматический режим NBFC означает **программную кривую**, не передачу управления обратно EC.
- Обычный рейтинг конфигураций NBFC подменяет аппаратные Lua-функции ответом 1. Проверки идентификатора/разрешения этого профиля могут не пройти такой рейтинг. Не удалять их ради оценки. Сам рейтинг не является испытанием аппаратуры.
- NBFC может предупреждать об отсутствии точки 0% в кривой. Для этого профиля отсутствие остановки намеренное.
- JSON ограничен размером менее 32768 байт, как требует исследованная реализация NBFC. Общая Lua-логика загружается на первом чтении; запись без этого шага запрещена.

## Проверки и публикация

Офлайн-тесты исполняют Lua 5.4 из готовых обработчиков с подставными файлами и ответами ACPI. Зависимость только для тестов: Lupa 2.8. На ноутбуке для работы профиля Lupa не нужна; Lua предоставляет сам NBFC.

Пересборка без доступа к оборудованию: [python3 build_profile.py](build_profile.py:1). Тестирование после установки тестовой зависимости в отдельное окружение: [python3 -m unittest discover -s tests -v](tests/test_profile.py:1).

Не проверялись на Linux: запуск штатного парсера/службы NBFC, загрузка acpi_call, реальное выполнение управляющих команд и температурное поведение. Офлайн-тесты не заменяют эти этапы.

Публиковать только как **EXPERIMENTAL / UNTESTED ON HARDWARE** с точной платформой и описанием нестандартного выхода на максимальную скорость. Не включать в репозиторий оригинальный отчёт ACPI, iGameCenter, бинарники инструментов, приватные журналы или какие-либо ключи. Перед обозначением профиля как рабочего нужны реальные результаты испытаний; для распространения выбрать подходящую лицензию. Профиль для Windows в этот пакет не входит.
